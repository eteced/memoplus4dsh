# M11 — 召回失败 case 分析报告（run-2 结果）

> English: [m11-case-analysis.en.md](m11-case-analysis.en.md)

> 日期：2026-09-05 · 数据：MemoryAgentBench 第二轮有效成绩（审计 PASS 的那轮）+ 全量归档会话日志 + 终态记忆图
> 范围约定（用户要求）：**只关注记忆系统没有正确召回的情况**，模型拿到记忆但没用好的情况不在本报告范围。
> 分析工具：`benchmark/analyze_recall_failures.py`（逐题归因）+ `benchmark/replay_retrieval.mjs`（离线检索复现），产物 `results/analysis/recall-attribution.json`（1100 题逐题判定）。

## 1. 归因方法

对每个可判定的题（答案词 ≥4 字符且非纯数字，共 1027/1100 题），检查支持正确答案的事实的去向：

| 判定 | 含义 | 责任方 |
|---|---|---|
| `injected` | pre-step 注入块里已有答案支撑事实 | 记忆系统已尽责 |
| `searched` | 注入没给到，但某次 `memory_search` 的结果里有 | 注入排序弱点 |
| `never` | 注入与全部 `memory_search` 结果里都没有 | **记忆系统召回失败（本报告对象）** |

对 `never` 再分：模型搜过仍 miss（纯检索失败）/ 模型没搜过（注入失败+模型未主动回忆）；并对照终态记忆图判定答案事件是否入图（CR 各 config 共享事实池，已验证四档答案词 20/20 在图，故 CR 的图归因可信；LME 图只剩最后一个 context，仅供个例参考）。

**proxy 局限**（诚实声明）：答案词字符串包含是召回的近似判据——MH 题模型可经中间跳事实推理出答案而答案词从未出现（召回率被低估）；常见答案词（如 English）的图内共现检查虽已加"同事件含查询内容词"约束，仍有少量假阳性。结论以量级为准，个案以 replay 实证为准。

## 2. 总体数字

全量 1027 可判定题：**注入召回率 7.7%，最终召回率（注入∪搜索）55.6%**。

541 道失败题的归因：

| 归因 | 数量 | 占比 |
|---|---|---|
| 已注入但答错（纯模型侧，排除出本报告） | 9 | 1.7% |
| 搜到但未利用（记忆最终给到，模型没答对） | 164 | 30.3% |
| **从未召回（记忆系统召回失败）** | **368** | **68.0%** |
| ├ 模型搜过仍 miss（纯检索失败） | 164 | |
| └ 模型没搜过（注入失败为主） | 204 | |

从未召回的 368 题的图归因（CR 可信）：图中有"答案+内容词"事件 **230**（读取链路丢的）、仅答案弱证据 57、图中无答案 81（其中 77 是 LME 图覆盖不全的伪信号；**CR 侧确认抽取丢失仅 ~4 题**）。

分 config 的关键形态：

| config | 注入召回 | 最终召回 | 失败中从未召回 | 主因形态 |
|---|---|---|---|---|
| sh_6k / sh_32k | 8.0% / 9.1% | 74% / 72% | 26 / 28 | **模型没搜**（24/26、27/28）；检索本身几乎不 miss |
| sh_64k / sh_262k | 3.0% / 2.0% | 69% / 68% | 29 / 31 | 搜过 miss 与没搜各半 |
| mh_6k~262k | **0%** | 52%~63% | 37~48 | **搜过仍 miss 为主**（25~43/config）——真·检索失败 |
| LME | 24.8% | 24.8% | 88 | **模型几乎不主动搜**（84/88 未搜），注入质量即天花板 |

一句话：**CR 的抽取几乎是好的（~4 题丢失），瓶颈全在读取链路；而读取链路里，pre-step 注入通道（CR 0~9%）远比 memory_search 通道弱。**

## 3. 根因（按证据强度排序）

### RC1 实体碎裂：同一实体裂成几十个节点

**量化**：终态图 15561 实体中，**2820 组重名、涉及 7125 个节点（45.8%）**。极端例：`william shakespeare` 35 个节点、`donald trump` 27 个。

**机制**（三层叠加，全部在代码里定位）：
1. 抽取模型对同一实体的类型判定逐轮翻转（PERSON↔CONCEPT）——`known_entities` 提示只给名字**不带类型**，模型每轮重新猜；
2. `createOrResolve` 的精确匹配**按类型过滤**（`store.ts` `findEntityByName(name, type)`），类型不同即新建；
3. 嵌入近似合并**根本没接线**——插件入口 `index.ts` 构造 `MemoryStore` 时没传 `embedder`，`resolveByEmbedding` 是死代码路径；且它也按类型过滤。

**后果**：实体锚定（查询提到的实体→其全部事件）和一跳扩展都被切碎——"Valmiki" 裂成 3 个节点，事实散在三个孤岛上。这是 MH 题"搜过仍 miss"的最大结构性原因。

### RC2 模板/指令文本污染：噪声事件霸榜

**replay 实证**（sh_6k q9，答案 Jonathan Rothschild，图中恰有且仅有 1 条金事件）：

- 净查询 `"What is the name of the current head of the Tucson government?"` → **金事件 rank #1**；
- 真实评测查询（官方模板包装：600 字符指令 + 示例问答 + 问题本体）→ **金事件跌出 top-12**，top-7 全是模板噪声事件：
  - `You need to answer a question based on this rule.`（指令句被抽成了事实）
  - `Based on the provided example knowledge pool, the current president of Russia is Donald Trump.`（**模板里的示例答案变成了假记忆事实**）
  - `User asked the Assistant to answer a question based on the rule...`（query 阶段的问答行为被抽取，见 RC3）

**机制**：模板文本经两条路进图——ingest 阶段（chunk 里带指令）与 query 阶段（每个 `bench-q*` 会话的 turn/end 都触发抽取，问题文本和模板示例被当成新事实）。这些事件与**每道题**的查询共享大段逐字文本，dense 与 IDF 通道都给满分。query 阶段产生的 `asked`/`answered` 言语行为事件虽仅 ~113 条（占 0.5%），但因"和问题长得一模一样"而精准霸榜。

### RC3 注入通道近乎失效

CR 注入召回率 0~9%。除了 RC2 的噪声霸榜，还有结构性因素：注入把**整个模板包装文本**当检索查询（`inject.ts` 取 user message 全文），问题实体在 600 字符查询里被稀释；top-k=8 + 2000 字符上限在 20k 事件的图上太紧。对照：模型自己的 `memory_search`（查询短、聚焦实体）把 SH 的最终召回拉到了 68~74%——**同一套检索器，查询质量决定生死**。

### RC4 冲突版本：新旧共存时新值偏好太弱

replay 实证（mh_262k q4，Valmiki 语言问题）：旧值 `Valmiki wrote his notable works in Sanskrit` 排 #3，新值（English）不在图（见 RC5），但若新旧都在图，两者分差仅靠 DENSE 模式的提及新近度项（上限 0.3，低于实体奖励 0.5、远低于关键词通道）——近平局时新值不能稳定胜出。**状态去重只覆盖 goal_/todo_ 等桥谓词，一般事实的新旧冲突没有任何硬性偏好。**注入行首的时间标签（`[last month]` 这类）把分辨责任推给了模型。

### RC5 抽取丢失新值（少数但存在）

Valmiki 案例：知识池里"Valmiki → English"（新值）从未入图，图中只有 Sanskrit 旧值。全图 5 条 Valmiki 事件无一条含 English。量级：mh_262k 的 48 个 never 里仅 3 题确认图中无答案、14 题弱证据。**抽取不是主要瓶颈，但对"被更新的反事实"有选择性丢失倾向**——推测：抽取模型面对编号事实列表时，对同主语的后续行有合并/跳过的倾向（待 mini run 复核）。

### LME 特别记录

LME 形态完全不同：注入召回 24.8% 就是天花板——模型在 LME 上几乎不调用 `memory_search`（88 个 never 里 84 个没搜过），完全依赖注入。LME 的提升空间 = 注入通道质量（top-k、查询构造、时序算子覆盖）+ 引导模型对记忆类问题主动检索（系统提示侧）。

## 4. 结论

读取链路的三个可修复缺陷（RC1 实体碎裂、RC2 噪声霸榜、RC3 注入查询构造）解释了绝大多数召回失败；写入链路（抽取）基本健康。修复优先级与验证方案见 `docs/m11-iteration-guide.md`。

## 5. 修复验证（首轮，2026-09-05 晚）

已实施的修复（详见 `m11-iteration-guide.md` 各条目的实施标注）：

- **P0-A 实体消解**：精确匹配与嵌入合并均改为类型无关；known_entities 提示携带既有类型。（注意：只防新碎裂，旧图不自愈，需新图验证。）
- **P0-B 噪声压制**：抽取协议加 `KIND` 列，由抽取模型语义标记言语行为事件（`speechAct`），检索按标记 ×0.3 降权（v1 的英文谓词词表是语言 hardcode，已打回重做）；抽取 prompt 新增"不抽指令/元叙述"规则。
- **P1-A 注入查询提取**：LLM 查询分析器为主路（与查询扩展同一次缓存调用，原语言输出核心问题），标点启发式仅作兜底（v1 只靠启发式，同样是语言 hardcode，已打回重做）。

**replay 实证**（run-2 终态图，sh_6k q9，答案 Jonathan Rothschild，图中恰有 1 条金事件）：

| 查询形态 | 修复前 | 修复后 |
|---|---|---|
| 官方模板包装全文（修复前注入行为） | 金事件跌出 top-12 | 言语噪声被压出，但指令类噪声（requires/based_on 等）仍霸榜，金事件仍未进 top-10 |
| distill 后的问题行（修复后注入行为） | — | **金事件 rank #1** |

结论：P0-B 单独不足以解决模板霸榜，P1-A 是主导修复；RC1 的实体碎裂修复效果需经新建图的 mini run 验证。单测 132 全绿。注：表中 replay 是 v1（词表+启发式）的结果；v2（标记+LLM 蒸馏）机制不同、目标相同，效果由 mini-2 验证。
