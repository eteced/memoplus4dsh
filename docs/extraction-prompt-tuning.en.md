# Extraction-prompt tuning report — `opencode-go-extra/deepseek-v4.1-flash`

> 中文：[extraction-prompt-tuning.md](extraction-prompt-tuning.md)
>
> Generated tables: [ab-extraction-prompts.md](ab-extraction-prompts.md) (with the raw JSON records)
> Corpus and candidates: [../profiles/](../profiles/README.md)

Scope: **the extraction-stage prompt only** (`stages.extraction.prompt`) on this
route. Deliverables: one model-name-matched reference profile, one reproducible
measurement harness, and the numbers below. No benchmark run (explicitly out of
scope); every measurement is an A/B on **real turns produced by our own
deployment**.

## 1. Bottom line

1. **Adopted: candidate C (`extraction-c-format-bilingual`)** — its prompt text is
   the body of `profiles/deepseek-v4.1-flash.json`. It has one **robust** win:
   **language consistency of fact sentences on Chinese turns** — five same-batch
   comparisons, five wins, with almost disjoint ranges: baseline
   `18.5% / 30.5% / 40.2% / 42.9% / 49.6%`, C `49.6% / 56.7% / 70.4% / 80.1% / 84.5%`.
   Cost: about **+500 prompt tokens per call** (prompt 3098 → 5076 characters).
2. **Format compliance is "better on average, not robust"**: across five same-batch
   comparisons, column-count violations went **3 wins / 1 tie / 1 loss** and empty
   core fields **4 wins / 1 loss**. The losing batch is the official one
   (violations 10→20, empty core 12→24), and 19 of those 22 rows come from **one
   turn** (`s91-t1`, a long English task spec). C's format discipline is
   probabilistic; it collapses on long, list-heavy English turns.
3. **Neither hypothesis the tuning started from reproduced — no gain, stated plainly**:
   - *bare numbers / versions / booleans as entity names*: the baseline's
     value-shaped (hard) noise is already near the floor (1.2–1.7%); candidate A,
     which adds an explicit rule for it, *raised* it to 3.5%, and C is slightly
     higher than baseline on hard noise in 3 of 5 runs.
   - *nine model names collapsed into one entity*: across 206 calls / 200+ outputs
     `collapse` is **0 everywhere**, and on the fixture turn the nine model names
     were never extracted as entities at all. E1 lives in the **entity-merge**
     stage; this round could not and did not fix it.
4. **`thinking=low` is a net loss**: at the same `max_tokens: 8192`, `low` spent the
   whole budget on reasoning in 2/2 turns (`finish=length`, 0 visible characters) —
   this is exactly the production `extraction produced empty content` failure.
   With the 3× headroom (24576) it works, at ~8k completion tokens per call
   (72–80% reasoning) and 170–330 s. The reference profile therefore pins
   `reasoningEffort: "off"` + `maxTokens: 8192`.

## 2. Corpus: 18 real turns

`profiles/ab-corpus.jsonl` (one JSON object per line:
`id`/`kind`/`source`/`category`/`why`/`features`/`text`), generated by
`scripts/build-ab-corpus.mjs` from two real sources:

- **15 turns** rebuilt from the session logs `session.v3.jsonl.zstd` with the
  plugin's own `buildTurnText`. (Note: those logs are **concatenated zstd
  frames**, and Node's `zstdDecompressSync` decodes only the first — which looks
  like "session header, zero turns". `decodeSessionLog` in the script walks the
  frame/block headers for this reason.)
- **3 turns** taken verbatim from `extraction-pending.jsonl`'s
  `pending.job.turnText`, i.e. exactly what the production extraction call was
  handed (including turns rebuilt after a crash).

| Coverage class | Turns | Note |
| --- | --- | --- |
| config-keys | 6 | config-key names (`promptProfilesDir`, `extractionMaxRetries`…) dense |
| model-names | 6 | model names dense, including the **E1 incident input** (`s12-t10`: the 9-model list) |

135,678 raw characters; 120,601 fed to the model. `--print-index` reproduces the

**Privacy note**: the corpus is real conversation content. It is not in the npm
package (`package.json` ships `lib` only) but does travel with the git repository.

## 3. Method and harness

| Script | Role |
| --- | --- |
| `scripts/build-ab-corpus.mjs` | builds/validates the corpus; `--print-index` prints coverage |
| `scripts/build-candidate-profiles.mjs` | wraps `candidates/*.prompt.txt` into loadable `candidates/*.json`, validated with the plugin's own `validateProfiles`; `--check` works as a CI gate |
| `scripts/ab-extraction-prompts.mjs` | the A/B itself: calls the endpoint the way the plugin does (**streaming** + `include_usage`, configurable `thinking` / `max_tokens`) and scores the raw pipe table with the plugin's own `parseExtractionOutput`; `--score-raw` re-scores a saved run offline (**a new metric costs zero calls** — that is how the language metric and the hard/soft split were added) |
| `scripts/audit-literal-entities.mjs` | measures the same name classes in the **live graph**, separating subject-side names (from `CANONICAL_NAME`, the tuning target) from legitimate object-side ones |

Metric definitions are in the script comments, so the goalposts cannot be moved
after the fact:

- **literal-noise**: share of rows whose `CANONICAL_NAME` matches one of eight
  shapes. **hard (a value, never a name)** = `number`/`version`/`boolean`/`quantity`;
  **soft (an identifier, which may legitimately be the topic of a technical fact)**
  = `camelCase`/`SCREAMING_SNAKE`/`filename`/`path`. Reported separately: treating
  `src/extraction.ts` as a subject can be right; treating `8192` as one never is.
- **langMatch**: share of rows on Chinese turns (CJK ≥15%) whose `NORMALIZED_FACT`
  is **actually written in Chinese** (≥4 CJK characters and ≥25% of non-space
  characters), so that `User said "可以的没问题".` — an English sentence quoting a
  Chinese phrase — is not counted as Chinese, which is exactly what would hide the
  defect being measured.
- **collapse**: rows whose canonical+aliases carry ≥2 distinct model names (the E1 shape).
- **format compliance**: `parseFailLines` (contains `|` but does not parse),
  `colMismatch` (field count ≠ 9), `headerEcho`, `emptyCore` (empty PREDICATE or
  NORMALIZED_FACT).

**Controlled input**: every call gets `{known_entities}`=`(none yet)` and
`{candidate_mentions}`=`(none)`, so candidates are compared on the turn text alone.
That is not the production input (production passes a relevance-filtered known-name
list), so a profile that only wins with a populated list would not show it here —
a known blind spot.

Calls and cost (all real calls):

| --- | --- | --- | --- |

| **Total** | | **206** | |

Reading it:

- **Language consistency (robust)**: all five same-batch comparisons favour C, and
  the five baseline values (18.5/30.5/40.2/42.9/49.6) barely overlap the five C
  values (49.6/56.7/70.4/80.1/84.5). This is the only metric where an "it works"
  claim is justified. Caveat: C's absolute level is still only 50–85% — it is
  *clearly steadier*, not *fixed*. (The "draft D" batch is default vs D and is not
  part of these five.)
- **Format compliance (unstable)**: column-count violations 3 wins / 1 tie /
  1 loss (21→2, 3→2, 2→2, 2→0, official 10→20); empty core fields 4 wins / 1 loss
  (16→6, 5→2, 3→0, 1→0, official 12→24). The official reversal comes entirely from
  `s91-t1`: there C produced 117 rows, 19 column mismatches and 22 empty core
  fields; the same turn in run1 was 1/4, and in the C-vs-D batch C returned nothing
  at all. **C's format constraints help on most turns but collapse on long English
  list-heavy turns; they are not a guarantee.**
- **literal-noise (no difference)**: C is lower 3 times, roughly equal twice, and
  *higher* on the hard class in 3 of 5 runs (2.4% vs 1.2%, 0.8% vs 0.0%,
  0.7% vs 0.5%). **No reliable improvement, hard class included.**
- **Events / completion tokens (no difference)**: C is sometimes cheaper
  (26282 vs 36514, 6969 vs 9354) and sometimes more expensive (36006 vs 31362,
  40.9 vs 32.7 events/turn). **No token-savings claim.** The one reliable cost is
  input: prompt 3098 → 5076 characters, measured at **+500 prompt tokens per call**
  (official batch 58106→67106, C-vs-D 27837→31837, repeats 19653→22653 — identical
  in all three).
- **D (A+B+C stacked) loses to C on both axes** (literal 22.7% vs 16.4%, langMatch
  59.8% vs 80.1%, same batch), and in the other batch D's literal 23.8% / hard 2.7%
  is worse than baseline 15.5% / 1.9%. **Rule stacking is not free: rejected.**
- **A gets worse on its own target metric** (hard 1.7%→3.5%, column mismatches
  21→26, parse failures 0→2). **Rejected.**
- **B cuts SCREAMING_SNAKE from 45 to 8**, column mismatches 21→5, empty core 16→7,
  but language consistency drops to 37.6% (whole turns flip to English) and it
  produces the fewest rows. **Rejected** (this round weights language and format higher).

### 4.2 Variance: the baseline swings from 0% to 97% on the same turn

Six turns, three samples each; the baseline's share of Chinese fact sentences per turn:

```
s9b-t1   92% / 93% /  6%      s9b-t4   81% /  0% /  0%
s12-t10   0% / 90% /  0%      s9b-t10  10% / 97% / 96%
s92-t1   38% / 14% / 40%      s44-t1   48% / 48% / 55%
```

C is far steadier on the same turns (`95/91/96`, `100/86/97`, `48/36/90`,
`100/97/97`, `36/23/18`, `35/47/50`). **The language drift is mostly sampling
instability, not a stable property of the prompt; C's value is that it suppresses
it, not that it removes it.** Totals for that subset: langMatch 44.9% → 69.0%,
column mismatches 7 → 3, empty core 8 → 1, events/turn 34.6 → 31.3.

### 4.3 E1 (model-name collapse) does not exist at the extraction stage

| Turn | Model names mentioned | baseline collapse | A/B/C/D collapse |
| --- | --- | --- | --- |
| `s12-t10` (fixture, 9-model list) | 11 | 0 | 0 |
| All 18 turns × all candidates (206 calls) | — | **0** | **0** |

On the fixture turn the baseline never extracted the nine model names as entities
at all (they appear as an "available models" list, i.e. values rather than

### 4.5 Thinking sensitivity: turning thinking on is a net loss on this route

Only `thinking` changes (`disabled` = `{type:disabled}`; `low` = `{type:enabled, reasoning_effort:"low"}`):

| Configuration | Visible output | Reasoning tokens | Conclusion |
| --- | --- | --- | --- |
| `disabled` @8192 | normal (e.g. 3195 chars / 39 rows, 0 reasoning, 26 s) | 0 | works |
| `low` @8192 (2 turns) | **0 chars / 0 rows (2/2)**, `finish=length` | 8192 / 8192 | **budget eaten by thinking → the production "empty content"** |
| `low` @24576 (3× headroom, 4 turns) | works (0 empty), but 1/4 turns `finish=length` | 47075 / 65668 (72%) | 5× tokens, 6–10× latency |

| low @24576 (4 turns) | default | C |
| --- | --- | --- |
| events/turn | 109 | 83 |
| reasoning share | 72% | 80% |
| completion per call | ≈8.2k | ≈9.1k |
| average latency | 328 s | 172 s |
| literal-noise | 11.2% | 21.9% |
| langMatch | 58% | 55% |

**C's advantage disappears (and inverts) once thinking is on** (sampling plus the
budget being consumed by reasoning). This route declares `off`
(`settings.yaml`'s `reasoningEfforts."off":` with an empty value → pi-ai sends
`thinking: {type: disabled}`), so the reference profile pins
`reasoningEffort: "off"` + `maxTokens: 8192` and never needs the plugin's adaptive
degradation. If some same-named route does not declare `off`, the plugin's `adapt`
policy degrades to `low` and multiplies the budget by 3 (→24576): it works, but at
3–7 minutes per call the extraction queue falls badly behind. This agrees with the
README's "turning thinking off" section.

One more finding, unrelated to the prompt but real: **many facts hang off the
`User` / `Assistant` label entities** (baseline 113/719 ≈ 15.7%, C 87/553 ≈ 15.7%)

consequence of the turn text carrying only speaker labels, and **no extraction
prompt can fix it** (the extracted name *is* the label); it needs the labels mapped
to known names on the `buildTurnText`/injection side, or the speaker's identity
made visible to the extraction stage. Not touched this round, recorded only.

## 5. Recommendation and delivery form

### 5.1 Recommendation

- Reference profile body = **C's prompt**
  (`profiles/candidates/extraction-c-format-bilingual.prompt.txt`, byte-identical
  to `profiles/deepseek-v4.1-flash.json`, verified with `diff`).
- `match` carries the **model name only**:
  `{"match": {"model": "deepseek-v4.1-flash*"}}`, no `provider` — "the same model
  name means the same model", so any route serving it (future gateways, official
  lines) picks the profile up.
- Pin `maxTokens: 8192` + `reasoningEffort: "off"` (§4.5).
- A/B/D's rule blocks are **not** included (no gain or a loss), but they stay in
  `profiles/candidates/` with their prompt sources for the next round.
- **Honest expectation**: Chinese-turn language consistency is clearly steadier
  (≈50–85% vs 20–50%); format compliance is slightly better on average but not
  guaranteed; entity-name noise and output volume are unchanged; input cost is
  +500 tokens per call.

### 5.2 Delivery form: shipped-in-repo + manual copy (this round); built-in deferred

| Form | Pros | Costs / risks |
| --- | --- | --- |
| **In-repo + manual copy (this round)** | no code change; uses the existing v0.2 external-profile mechanism; the user can read the JSON first and revert with `promptProfile: default`; upgrading the plugin never silently changes behaviour | one manual step plus a restart; **not in the npm package** (`files` ships `lib` only), so npm users do not get the file and must copy it from git/docs |
| **Built-in shipped profile** (added to the default profile list in `src/prompts.ts` and registered) | zero-config for every user; versioned and testable; `memory_status` reports it | requires editing `src/prompts.ts`/`src/index.ts` (out of scope this round, and two other workstreams are editing those files); **upgrading would silently change every user's extraction behaviour** (a prompt change is a behaviour change); must keep `promptProfile: default` as the escape hatch |
| Inlining into `cordis.patch.yml`'s `promptProfiles` | works today | exactly the form v0.2 set out to remove: prompt text buried in user settings, unreviewable and unreusable |

**Same-name conflict risk (the user must know this)**: because matching is by model
name only, if another route later serves `deepseek-v4.1-flash` with different
behaviour (different quantization, fine-tune, or gateway trimming), this profile
applies to it too. Mitigations: the global `promptProfile: default` fallback, or
narrowing a local copy by adding `provider` back.

**Suggested next step on form** (next round, not now): add `profiles/` to
`package.json`'s `files` so npm users get the JSON too (still a manual copy, still
no default change); treat "ship as a built-in profile" as a deliberate
compatibility decision, with an "upgrade changes the default prompt" note and an
opt-out.

## 6. Limits

1. **Small n, large variance**: one sample per (candidate × turn) in the main
   tables; only 6 turns × 2 candidates got three samples. The same baseline moves
   a lot between runs (langMatch 18.5–49.6%, literal 5.3–20.7%, column mismatches
   2–21), so only **"same-batch comparison + direction consistent across runs"**
   supports a conclusion — which is why §4.1 exists.
2. **Controlled input**: `{known_entities}`/`{candidate_mentions}` are empty;
   production is not.
3. **Output-level only**: no graph-side quality (retrieval/injection/multi-hop
   recall) and no measurement of knock-on effects on entityMerge/supersede.
4. **The soft noise class needs human labelling** (§4.6).
5. **C returned empty output twice in 60 calls** (long English turns, `finish=stop`
   with 0 characters; baseline 0 in 90). The plugin retries empty content
   (`extractionMaxRetries`), so it is not fatal, but the sample is too small to rule
   out "this prompt triggers empty output more often"; the `s91-t1` collapse (117
   rows, 19 column mismatches) points the same way. **Next round should gate on
   empty-output rate and on long English turns like `s91-t1`.**

## 7. What the next round should do

1. **Tune `stages.entityMerge.prompt`** — where E1 actually lives. Its prerequisite
   is documented at the top of `scripts/ab-merge-prompts.mjs`: log the *complete*
   adjudication input (whole mention batch, candidates, aliases, known-fact text),
   otherwise the fixture cannot be rebuilt verbatim and the A/B stays a smoke test.
2. **Then `stages.supersede.prompt`** using the same method (corpus + output-level
   metrics + `--score-raw`).
3. **Turn the reference profile's A/B into an n≥3 gate**: a representative 8-turn
   subset × 3 samples, gating on `langMatch`, `colMismatch`, `emptyCore` and
   empty-output rate. `--score-raw` makes re-scoring free; only the calls cost.
4. **Decide the form**: add `profiles/` to npm `files`; decide on a built-in
   shipped profile (with an opt-out).
5. **Fix speaker identity** (§4.6): the `User`/`Assistant` label entities are a real
   fragmentation source that no prompt can fix.
6. **Human-label a small soft-noise sample** (e.g. 100 output rows marked
   "legitimate subject / illegitimate literal") to promote the metric from a shape
   proxy to one with ground truth; until then entity-name noise cannot be a gate.
